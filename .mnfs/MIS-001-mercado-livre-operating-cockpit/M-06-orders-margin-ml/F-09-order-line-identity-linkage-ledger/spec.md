# F-09 Stable Order-Line Identity and Linkage Ledger Specification

## Outcome

The orders module owns durable, opaque Mercado Livre order-line identities and
an append-only Postgres ledger that records one exact external-order to
internal-document mapping under tenant and installation scope. The seam does
not read Oracle or provider data and exposes no transport contract.

## Ownership and boundaries

- `orders/domain` owns line-identity and Sankhya-linkage value types,
  validation, semantic equality, and explicit reconciliation states.
- `orders/ports` owns the transactional linkage repository contract.
- `orders/adapters/postgres` owns persistence, transactionality, uniqueness,
  and idempotent retry behavior.
- Existing order ingestion remains the only consumer of order-item persistence.
  It may reconcile provider rows, but must never use mutable `line_no` or an
  ambiguous attribute tuple as identity proof.
- Refresh persistence updates rows by immutable `mpc_line_id`; it does not
  delete/reinsert retained identities. Removed unlinked rows may be deleted,
  while removal of a ledger-protected line fails with an explicit order-line
  identity conflict and rolls back the whole refresh.
- Future orders application services will consume the linkage repository port;
  this feature does not wire composition, application, transport, Oracle, or
  provider adapters.
- Domain identities are generic. Oracle table names, driver types, and provider
  payload DTOs do not cross into domain or ports.

## Stable line identity

Each persisted order item has:

- an opaque, immutable `mpc_line_id` generated by MPC; and
- a reconciliation state of `stable`, `legacy_unresolved`, or `ambiguous`.

Fresh imports assign a new ID and `stable` state. Refresh reconciliation groups
rows only by the provider identity fields persisted today: provider item ID,
variation ID presence/value, and seller SKU presence/value. A unique incoming
and persisted member retains its prior ID even when quantity, unit price, or
`line_no` changes. Quantity and unit price are mutable snapshot consistency
evidence, never identity-key fields.

When either side has multiple members for the same provider identity, the
whole group is `ambiguous` and non-linkable. Reconciliation preserves the
existing opaque ID multiset deterministically, allocating new IDs only for
genuinely new excess incoming members. Deterministic storage order may use
`line_no`, but no individual duplicate pairing is claimed as identity proof.
A previously ambiguous surviving group does not silently become stable merely
because its multiplicity later decreases. Existing migrated rows are explicitly
`legacy_unresolved`; their old `line_no` is not promoted to proof. Stale refresh
behavior remains unchanged.

## Linkage aggregate and repository port

The append request contains:

- scope: `tenant_id`, `installation_id`, and `provider_order_id`;
- exact account-scoped external order key
  `ml:v1:<installation_id>:<provider_order_id>`;
- exact internal header identity: generic document ID;
- every explicit line mapping: `mpc_line_id` to generic internal document-line
  identity;
- audit: event ID/type, actor ID/type, reason, idempotency key, source time,
  recorded time, optional previous-event reference, configuration revision,
  safe evidence state, and optional safe evidence reference.

The repository exposes one atomic append operation and a current-mapping load.
The append inserts the header event and all line events in one transaction. A
retry with the same scoped idempotency key succeeds only when its canonical
business and audit payload is semantically identical, returning the already
persisted aggregate. Same-key mismatch, reuse of a mapped MPC line, reuse of an
active internal origin line, missing order/line ownership, or non-linkable line
state fails closed without overwriting history.

## Persistence invariants

- Every linkage table carries `tenant_id` and `installation_id`.
- One current header mapping exists per tenant, installation, and provider
  order.
- The exact external order key is validated from installation/order scope and
  unique within the tenant and installation.
- One current origin mapping exists per provider order and MPC line.
- An internal origin document line cannot be actively assigned to two MPC
  lines in the same tenant and installation.
- Idempotency keys are unique per tenant, installation, and operation.
- All linkage rows are append-only; update and delete are rejected by database
  triggers.
- Foreign keys prove that a requested `mpc_line_id` belongs to the scoped
  persisted order. No lookup is scoped by provider order alone.
- Source time and recorded time are distinct and non-null. Unknown evidence is
  represented by an explicit evidence state, never by a zero document/line ID
  or fabricated reference.

## Migration and legacy decision

Migration `0033_orders_sankhya_linkage.sql` adds line identity columns, assigns
opaque IDs to existing rows, marks them `legacy_unresolved`, enforces scoped
identity uniqueness, and creates the append-only linkage tables and constraints,
including the exact external-order-key shape and scoped uniqueness. It does not
infer identity from `line_no` or mutable business attributes.

## Error behavior

Domain validation rejects missing scope, empty IDs, invalid state values,
non-positive internal document/line identities, incomplete audit data,
duplicate MPC line IDs within a request, and duplicate internal origin lines
within a request. Persistence returns stable not-found, conflict, and invalid
errors without exposing SQL or provider-specific details.

## Verification

### F09-AC01 Stable line identity

Fresh and refreshed order repository tests prove opaque ID assignment,
retention across a unique provider identity and reorder, explicit ambiguity for
duplicates, preserved duplicate ID sets, and unchanged stale-refresh behavior.

### F09-AC02 No positional or mutable proof

Domain and order repository tests prove that `line_no`, quantity, and unit
price never participate in the identity key and an ambiguous provider identity
group is not treated as proof.

### F09-AC03 Honest legacy state

Migration and domain tests prove existing rows receive opaque IDs in
`legacy_unresolved` state without an inferred match claim.

### F09-AC04 Atomic semantic idempotency

Repository tests prove one transaction inserts header and all lines, an
identical scoped retry returns the existing aggregate, and mismatched reuse
or external order key fails closed without overwrite. Confirmed linked orders
refresh in place, while attempted removal of a linked line returns the explicit
identity conflict without partially persisting the header refresh.

### F09-AC05 Scoped append-only constraints

Migration and Postgres tests prove tenant/installation scope, scoped line and
origin uniqueness, complete audit fields, and update/delete rejection.

### F09-AC06 Bounded proof and side effects

Focused Go and migration tests plus scoped diff inspection prove the seam. The
Postgres test is run only against the approved ephemeral target; no Oracle,
provider, production, secret, or PII access is permitted.

- Domain tests cover valid construction, invalid/unknown facts, semantic retry
  equality, duplicate lines, and explicit reconciliation states.
- Order repository tests cover stable refresh identity, reordering, ambiguous
  duplicates, legacy state, linked-row in-place refresh, removed-linked-line
  conflict, and unchanged stale-refresh behavior.
- Linkage repository tests cover atomic append, semantic idempotent retry,
  conflicting retry, scope isolation, line ownership, uniqueness, and
  append-only enforcement when ephemeral Postgres is available.
- Migration embedding tests prove migration 0033 is canonical.

No test or implementation may access Oracle, a provider, production data, or
install dependencies.
