The comment reads: *"The ERP side of seller_sku is the CODPROD, which a resolved product always has — so side=erp is reachable for seller_sku only through the listing, never through the product."* Both halves are wrong. `side=erp` is never reachable "through the listing" — the listing-empty case sets `SideProvider` (`generation_service.go:641-642`), which is what the case immediately below the comment (`:423-429`) actually asserts. And `side=erp` **is** reachable through the product: `generation_service.go:643` is `case product == nil || productValue == "":`, and `generation_service.go:215-217` builds the unresolved candidate with `newProviderIdentityAnchorComparison(snapshot, identityAnchors, nil)`, so any listing whose seller_sku, EAN and title all match nothing emits `seller_sku / INCOMPARABLE / side=erp`. I traced that it survives `appendProviderDeclaredUnavailableReasons`: with `comparison.product == nil` and a non-empty listing value, `classifyProviderIdentityAnchor` returns `emit=false` at `:722`, so the seeded `side=erp` reason is retained verbatim. Correct would be a sentence narrowed to the harness it governs ("with a resolved product present, `side=erp` cannot arise for seller_sku") or no sentence — R-25 says the false half is deleted or narrowed, never annotated. This hunk is one of the ten written inline, and the inline origin shows here: it is a comment written to justify a deletion rather than to describe the branch.

*"Depois do fix, `side=erp` é INALCANÇÁVEL para `seller_sku` — um produto ERP resolvido sempre tem CODPROD."* The second clause is true; the first does not follow from it and is refuted by finding 1. Net effect: the only seller_sku `side=erp` assertion in the suite was removed and justified by a claim the code refutes.
