## Findings

None rise to blocking. Two non-blocking items:

1. **[non-blocking]** `apps/server_core/internal/modules/erp_import/domain/import.go:50-67` (`ImportID.IsValid`) is stricter than Postgres `uuid_in`: it requires the canonical `8-4-4-4-12` dashed form and will reject a syntactically-valid-to-Postgres 32-hex-digit id with no dashes (or brace-wrapped form). Production never produces such an id — `import_service.go:210` always formats with `fmt.Sprintf("%08x-%04x-%04x-%04x-%012x", ...)` — so this cannot reject a real id, only an alternate-format client-supplied one, which is the conservative failure direction. Not a defect against the stated A8 contract (400-before-query), just worth the chip knowing the guard is a proper superset restriction, not an exact mirror of Postgres's grammar. What correct-if-desired behavior would look like: either leave as-is (recommended — a manufactured 32-hex-no-dash client id is not a realistic attack the endpoint needs to accept) or explicitly document the stricter-than-Postgres choice in the `IsValid` comment.
2. **[non-blocking]** The adversarial-question item above: the `TestCase3EANAloneYieldsMediaConfirm` assertion rewrite is traceable and symmetric with pre-existing precedent, but it does encode a direction label (`UNAVAILABLE`) that is itself acknowledged-imprecise for a "both-present-disagree" case. This is explicitly out of this chip's scope (A2-R1 AGAINST branch, operator's call) and was not introduced by this diff — flagging only so it does not get silently treated as "semantically correct" going forward.
