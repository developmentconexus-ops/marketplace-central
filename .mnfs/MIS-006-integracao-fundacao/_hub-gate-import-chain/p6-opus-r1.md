### Answers to the specific attack questions

- **Priority 1 (wiring, the unproven half).** Real composition: `main.tsx:19-23` `ClientProvider > QueryClientProvider > App` → `AppRouter.tsx:59-61` `BrowserRouter > InstallationProvider > Routes` → `Layout` → `routes/importacoes.tsx:9` → `ImportacaoDetailPage` → `ImportChainPanel` → `useErpImportChain` → `useClient()` + `useQuery`. **Both required contexts are ancestors; no lazy import, no decorator, no optional port, no key derivation from context.** The decorator-drop risk is `ClientProvider`'s spread — `...createMarketplaceCentralClient({ baseUrl, fetchImpl })` (`ClientContext.tsx:23`) — and `getErpImportChain` is an own enumerable method of the returned object literal (`sdk-runtime/src/index.ts:1901`), so it survives the spread. Query keys are disjoint: `["erp-imports","chain",id]` (`useErpImportChain.ts:6`) vs `["erp-imports","detail",id]` / `["erp-imports","list"]` (`pages/vinculos/useErpImports.ts:10-11`). The test mock's rejection shape `{ status: 404, error: "import_not_found" }` (`ImportChainPanel.test.tsx:127`) **is byte-equal to what the real transport produces** (chain verified above through the Go handler) — that is the one place a mocked rejection could most plausibly diverge, and it does not. Production `QueryClient` has `retry: 1, refetchOnWindowFocus: false` and **no `throwOnError` and no error boundary** (`web-query/src/index.ts:82-91`), so the panel's own error branch is what runs in the app, exactly as in the tests. I found **no** wiring path where the mock diverges from the app.
- **Priority 2 (what the enumeration MISSED).** SDK declares all five fields non-optional, non-nullable (`packages/sdk-runtime/src/erpImport.ts:48-54`); OpenAPI declares them `required` (`contracts/api/marketplace-central.openapi.yaml:8080`); Go emits `int` + RFC3339 (`http_handler.go:133-138`).
