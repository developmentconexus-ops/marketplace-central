F4 — fold CatalogAssortmentReader into CatalogPageReader
========================================================

WHY THIS IS NOT A LOCAL FIX
---------------------------
`go test ./...` was red on tests/unit with 503 source_unavailable. The cheap fix
(a stub with pass-through WithPolicy methods that discard the policy, plus
?include_all=true on the request) was written and REJECTED: it makes the test
pass with the assortment cut completely broken, and the query parameter routes
around the seam the test is supposed to exercise. Operator ruling: no mock, no
fallback, real validation; blast radius is not a reason to stop at a local
maximum.

Root cause is a type-level one, and it has three symptoms in three layers.


MUST-FAIL 1 — a wiring fault reported as an infrastructure fault
----------------------------------------------------------------
    go test ./tests/unit/ -run 'TestComposedCatalog|TestComposedLinkage' -count=1

    --- FAIL: TestComposedCatalogHTTPNoCacheBypassesAndRepopulates (0.00s)
        cache_composed_test.go:111: GET /catalog/products status=503 body={"error":"source_unavailable"}
    --- FAIL: TestComposedLinkageConfirmEvictsCatalogButPreservesPriceCost (0.00s)
        cache_composed_test.go:198: GET /catalog/products status=503 body={"error":"source_unavailable"}

Nothing is unavailable. The transport asked for the tenant's stored assortment
rule (policy = nil, the "ask the routing seam" encoding), the test wired the
cache decorator straight to the transport with no routing seam in front, and the
cache correctly refused to key an entry under an unresolved policy. That refusal
came out of writeCatalogPageError as 503 source_unavailable, because that
function's last branch maps EVERY unmatched error to that code. An operator
reading this would restart Oracle.


MUST-FAIL 2 — the defect the 503 masks
--------------------------------------
The nil-policy guard fires before the type assertion, so the more serious fault
never gets reached on that path. Driving the same chain with a concrete policy
(temporary probe tests/unit/zz_probe_panic_test.go, deleted after capture):

    panic: interface conversion: *unit.composedCatalogOracleReader is not
    ports.CatalogAssortmentReader: missing method GetCatalogAssortmentCounts
      .../internal_read/adapters/cache/cache.go:342
      .../internal_read/adapters/cache/cache.go:187

A type error, at runtime, inside an HTTP handler, on a fact the compiler had in
hand at build time.


THE CLASS — 12 sites, 3 layers
------------------------------
Every seat in the live catalog chain declares a narrow downstream and then
asserts its way back to the wide one:

    cache/cache.go:342, :373, :383, :434, :438, :442        (6)
    internal_read/application/service.go:51, :63, :67       (3)
    internal_read/observability/timing.go:111, :136, :148   (3)

plus cache/cache.go:417, which discards the `ok` outright:

    pages, _ := downstream.(internalreadports.CatalogPageReader)

leaving a nil field for a later call to dereference. The compile-time asserts at
cache.go:312-313 do not catch any of this: they prove the DECORATOR implements
both ports, and the decorator implements the wide port by asserting on its
downstream. The assert certifies the façade, not the chain.


WHY FOLDING, AND NOT "CatalogSource = both ports"
-------------------------------------------------
Census of every non-test implementer of CatalogPageReader:

    erp_import/adapters/internalread/reader.go      both
    internal_read/adapters/cache (CatalogPageReader) both
    internal_read/adapters/cache (Reader)            both
    internal_read/adapters/oracle/catalog_page.go    both
    internal_read/adapters/routing/reader.go         both
    internal_read/application/service.go             both
    internal_read/observability/timing.go            both
    catalog/adapters/internalread (Reader)           narrow only
    catalog/adapters/internalread (UnavailableReader) narrow only

and ports/catalog_page.go:142 claims, verbatim:

    "CatalogAssortmentReader is OPTIONAL, and only the Oracle reader implements it"

Seven implementers, not one. The comment is a false universal in a contract
file, so it is deleted rather than softened (R-24/R-25).

The two narrow-only types are the catalog module's pass-through reader and its
UnavailableReader, which answers every method with the same stored error. Both
can carry the fold honestly — UnavailableReader returning its error for the
assortment methods is not a fallback, it is the same honest refusal it already
gives for the other nine.

So "optional" was never true. The optionality was maintained by hand, paid for
with 12 assertions, and each of those assertions is a place the chain can be
mis-wired without the compiler noticing.

Second redundancy, found while measuring the fold: the narrow triple is
EQUIVALENT to the wide one at every seam,

    routing/reader.go:120  ListCatalogProductFacts -> ListCatalogProductFactsWithPolicy(..., nil)

with exactly one exception — the cache, where the narrow path builds its key
WITHOUT assortmentKey(). Two entries for the same read, one of them not keyed by
the cut. In production nothing reaches it (routing resolves the policy above the
cache, so the cache only ever sees the wide call), so what is actually there is
a dead duplicate method set whose one distinguishing behaviour is a latent
cross-policy cache-poisoning key.

END STATE: one port, four methods, zero runtime assertions.

    type CatalogPageReader interface {
        ListCatalogProductFacts(ctx, Cursor, int, *SellableAssortmentPolicy) (CatalogFactPage, error)
        SearchCatalogProductFacts(ctx, string, Cursor, int, *SellableAssortmentPolicy) (CatalogFactPage, error)
        CatalogProductFactsByIDs(ctx, []int64) (CatalogFactPage, error)
        GetCatalogAssortmentCounts(ctx, *SellableAssortmentPolicy) (CatalogAssortmentCounts, error)
    }

CatalogProductFactsByIDs deliberately keeps no policy: it serves "these exact
ids", which the linked-listing screens need to resolve regardless of the cut.

RequireAssortmentPolicy stays. With the fold it is no longer reachable from a
mis-wiring, only from a caller that genuinely passed nil past the routing seam,
which is the honest-unknown refusal it was written to be.

After the fold, must-fail 2 is not a runtime panic. It is a compile error, and
the offending test does not build at all.
