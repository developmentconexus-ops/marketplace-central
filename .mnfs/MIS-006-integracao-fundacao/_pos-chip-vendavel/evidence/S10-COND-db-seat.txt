== FINDING — the sentinel is in NO harness lane ==

Reported, not fixed: the lane's package list is a seam, and this is a hub call.

`harness.ps1 integration` was run first, and it passed:

    target=ephemeral-postgres
    migrations_first=72
    migrations_second=0
    port=55840
    status=passed
    run_id=4aa2c34444d649aca437f5bb543085cc

It ran ZERO tenant_config tests. Get-HarnessIntegrationTestPackages
(scripts/harness/Postgres.psm1:42-61) discovers module packages by scanning the
FIRST FIVE LINES of every internal/modules/**/*_test.go for

    ^//go:build\b.*\bintegration\b

No file in internal/modules/tenant_config carries that tag — repository_test.go
line 1 is `package tenant_config_test`. So:

  - the integration lane never compiles the package, and says nothing about it;
  - the unit lane (`go test ./tests/unit/...`, harness.ps1) does not reach
    internal/modules at all;
  - a bare `go test ./...` at a seat with no MPC_TEST_DATABASE_URL reaches it and
    SKIPS clean, by design (testpostgres.SkipWithoutTarget, target.go:47-52).

Three lanes, three silences. A DB-touching test with no build tag is invisible to
the lane that provisions a database and skip-clean everywhere else, so it can rot
green indefinitely. `status=passed` from that lane is not a statement about it.

This is the same shape as HARNESS-DEBTS B-5 ("variável setada != banco
alcançável") one level up: there the env var was set and the database was absent;
here the lane is green and the test was never compiled. Both make a green a
statement about something other than what the reader thinks.

Also measured while confirming the above: the lane DROPS its per-run database at
the end. After `status=passed`, the session container held only
postgres/template1/template0 — which is why this seat had to create and migrate
its own database rather than reuse the lane's.
