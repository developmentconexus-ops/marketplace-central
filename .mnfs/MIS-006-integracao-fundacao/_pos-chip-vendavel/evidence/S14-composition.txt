== THE CLASS THIS SLICE CLOSES (A-24) ==

"Production composition decides behaviour and no test MOUNTS the production
composition."

catalog/transport's Register (http_handler.go:82-98) branches:

    _, hasRouteClasses := mux.(routeClassRegistrar)
    if h.PageReader == nil && !hasRouteClasses {
        mux.HandleFunc(catalogListPath, h.handleLegacyProducts)      // UNCUT page, no counts
        mux.HandleFunc("GET "+catalogSearchPath, h.handleLegacySearch)
    } else {
        registerInteractiveRoute(mux, catalogListPath, h.handleProducts)   // cut page
        registerInteractiveRoute(mux, catalogSearchPath, h.handleSearch)
        registerInteractiveRoute(mux, catalogCountsPath, h.handleCounts)   // the N/M counter
    }

Which branch production takes decides whether the sellable cut reaches the
catalog screen at all, and whether /catalog/products/counts exists. root.go:280
builds httpx.NewRouteClassMux() and root.go:531 calls Register on it
unconditionally. Nothing asserted that. A stand-in mux in a transport unit test
cannot assert it, because the branch is chosen BY the mux type the composition
passes in — so the test mounts NewRootRuntime.


== THE FIRST VERSION OF THIS TEST WAS VACUOUS ==

Recorded here deliberately. The first version probed for 404 on the counts path
and for 405 on POST to the list path. BOTH must-fails passed GREEN
(scratchpad/s14-run.txt: `--- PASS: TestRootRuntimeDoesNotRegisterLegacyUncut
CatalogRoutes` under both mutations). Root-caused by instrumentation, not by
reasoning:

  - "/catalog/products/counts" is matched by the wildcard pattern
    "GET /catalog/products/{id}" (http_handler.go:96) with id="counts" whenever
    the counts route is absent. The path is therefore NEVER a 404 in either
    world — it is answered by the wrong handler.
  - handleLegacyProducts performs its OWN method check and replies 405, so a 405
    on POST is identical in both worlds.

This is the CHIP-IMPORT-CHAIN class — "an observable that passes in BOTH worlds is
not evidence" — committed by me, in the slice whose whole purpose was to catch an
unasserted branch. It was caught only because the must-fails were run before the
slice was accepted. The trap is documented in the test's own doc comment
(catalog_routes_test.go:22-35) so the next reader does not re-probe the same way.

The rewrite measures the discriminators first and then asserts on them. Three
assertions, none of them a status-alone probe:

  1. GET /catalog/products/counts must be 503 (the cut page's honest
     source_unavailable), NOT 400 invalid_identity from the {id} handler.
  2. GET /catalog/products must be 503, not the legacy handler's internal error.
  3. POST /catalog/products must be 405 AND its body must not contain
     CATALOG_METHOD_NOT_ALLOWED — the router's 405 is plain text, the legacy
     handler's is the module's JSON envelope. The status is the same in both
     worlds; only the body names who answered.
