TIPAGEM DE details POR CODIGO — narrowing GANHO, nao asserido
  Conflito que motivou: o EXEMPLO-IO exige `e.details.allowed_range` tipado string,
  mas no contrato `allowed_range` NAO esta em nenhum `required` (schema flat nao
  consegue dizer "obrigatorio so para 3 dos 9 codigos"). Tipar como string puro seria
  o SDK afirmar garantia que o contrato nao faz. Ruling do hub @4f086d6c aprovou a
  saida: mapa por codigo + hasCode VALIDANDO em runtime os campos mapeados.

  ApiErrorDetailsByCode: invalid_erp_source/invalid_limit/invalid_ids -> allowed_range
                         missing_required_column -> column
                         duplicate_file -> import_id, protocol

  CORRECAO DE MEDICAO sobre o rascunho do chip: `import_in_progress` foi REMOVIDO do
  mapa. O rascunho o listava com {import_id, protocol}; a leitura de
  erp_import/transport/http_handler.go:185-188 mostra `apierror.Write(..., nil)` —
  details e nil. So duplicate_file (linhas 177-184) popula. O mapa segue o que o
  handler EMITE, nao o que seria simetrico.

  hasCode(e, C) retorna FALSE se o code casa mas o campo garantido falta ou nao e
  string. Consequencia deliberada: o consumidor cai no ramo generico em vez de ler
  undefined com o tipo dizendo string. E isso que torna o tipo honesto.

GUARD DE DRIFT ENTRE O TIPO E O CHECK (correcao do chip sobre o worker)

  SINALIZOU com honestidade o buraco: mapa e interface podiam divergir sem tsc

  enquanto o runtime nao valida. Fechado com mapped type:

      [C in keyof ApiErrorDetailsByCode]: readonly (keyof ApiErrorDetailsByCode[C] & string)[];
